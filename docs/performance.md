# 性能与机制结论

两个已实测的性能决策。改导出 / 无头子进程前先看这里, 不要重复试错。

## 导出: SB3U 占 2.3s, 暂不替换

一次导出 3.6s, 其中 SB3U 外部进程占 2.3s, 流水线其余部分合计约 0.9s。原来猜的"每次全量重写 56MB u3d,
约 200MB 磁盘 I/O"不成立: 写回只占 0.21s, 合并材质只占 0.03s。

实测拆分 (沙箱 `Morwyn`: u3d 54MB, 约 1.1 万个对象 / 1 个网格 / 3 个材质; 拿真实生成的 SB3U 脚本做减法):

| SB3U 里的一段 | 耗时 |
|---|---|
| 读 + 解析 u3d (`OpenUnity3d`) | 0.89s |
| 开 animator + 传输骨架 (`BeginTransfer` / `OpenVirtualAnimator` / `EndTransfer`) | 0.39s |
| 替换网格 (`MergeFrame` + `ReplaceMeshRenderer`) | 0.59s |
| 写回 54MB (`SaveUnity3d`) | 0.21s |
| 导入 fbx (`ImportFbx`) | 0.19s |
| 合并 3 个材质 | 0.03s |
| 合计 | **2.30s** |

- u3d 是**未压缩**的 UnityFS: 54MB = 6 张贴图 48MB + 9 个 Mesh 4.5MB + 约 1.1 万个 GameObject / Transform 小对象。
  写回便宜, 贵的是 SB3U 打开时建对象图; 同一 animator + 网格重复替换 8 次只多 0.4s, 大头是"打开一次 + 首次传输"的固定开销。
- UnityPy 直接换网格的**写回这一半已验证可行**: `UnityPy.load(54MB)` 0.13s / `bundle.save()` 0.22s / 写盘 0.06s,
  11397 个对象往返逐个原始字节 sha1 比对完全一致。理论上 2.3s 可压到 ~0.5s (导出 3.6s -> 约 1.7s)。
- 但难的部分全要自己重写: fbx 顶点 / 法线 / UV / 切线 / 蒙皮权重解析 (现在 `fbx.py` 只读元数据)、按通道布局造 Unity 网格、
  `bones="Replace"` 的骨骼映射与 `m_BindPose` / `m_Skin` 重建、头模形态键、材质槽位 (`_MainTex` / `Spec` / `Norm`)。
- **回归风险高, 而且写错不会当场报错**: 失败方式是"导出成功但模型是坏的" (蒙皮错 -> 变形穿模, 法线切线错 -> 光影歪,
  材质槽错 -> 贴图错位, 子网格顺序错 -> 部件用错贴图, 包围盒错 -> 部件消失), 只能游戏里肉眼看。
- 结论: **先不动**。收益 1.9s, 代价是把成熟上游工具换成自己维护的二进制写入器, 且影响面是整个核心功能。
- 将来真要做, 唯一低风险的切入方式: 把 SB3U 当参照实现做等价性测试 (同一份 fbx / u3d 两边各跑一遍, 用 UnityPy 逐字段比对
  顶点 / 法线 / UV / 骨骼索引 / 权重 / 子网格 / 材质 / 包围盒), 一致才替换, 并做成常驻测试。仍是多天到多周的项目。

## 常驻导出子进程: 5.8s -> 3.6s

`Morwyn.blend` 12.3MB / u3d 56MB / zipmod 72MB, 热态:

| 路径 | 用户等待 |
|---|---|
| 一次性子进程 (原来) | 5.83s |
| 常驻导出子进程 (现在) | **3.6s** (首次 5.3s, 含拉起它 1.2s) |

一次性子进程多出的 2.7s 全是进程开销: Blender 启动 0.61s + 载入 `.blend` 0.42s + `import UnityPy` 1.17s +
`import` 插件模块图 0.10s + spawn / 退出 ~0.35s。常驻进程启动时先在后台线程 `import UnityPy` 预热, 所以只有首次多花 1.2s。

机制 (操作要点见 `AGENTS.md`): 主进程 `save_blend_file()` 后把 (工程路径, 脚本路径) 发给端口 14147;
常驻进程在**主线程** `bpy.ops.wm.open_mainfile()` 换掉整个数据库再跑脚本, 所以上个任务的脏状态不会残留;
单实例靠端口, 代码改过就按文件修改时间重启; 三种异常 (30s 内没就绪 / 半路被关掉 / 端口被占) 都退回一次性子进程, 下次导出自动重开。

## 为什么导出不能在主进程内跑

要求是"对工作进程完全无副作用, 且撤销 / 恢复照常可用"。Blender 的机制做不到, 隔离只能靠进程:

- **一个进程只有一个 `bpy.data`**: `bpy.ops.wm.open_mainfile()` 整库换掉, 连 Python 侧旧引用都会变死
  (`ReferenceError: StructRNA of type Object has been removed`); 多开 `scene` 也不行 (场景共享同一个 `bpy.data`)。
- **没有事务 / 回滚 API**: 唯一的批量回滚是全局撤销, 但 `-b` 模式下 `bpy.ops.ed.undo()` 直接 poll 失败;
  界面里能用但会占掉用户那一步撤销; 而且只管数据块, 管不了磁盘写入。
- `bpy.context.temp_override` 只换上下文不改数据, 不构成隔离。
- "导出前存快照 -> 导出后 `open_mainfile` 回去"能还原文件, 但整个会话连同撤销历史一起没了。
- 让导出流程自己只改副本 (深拷贝 + 重链接 + 隐藏原件) 技术上可行, 但流程里到处是按名字取物体、
  `export_scene.fbx(use_visible=True)` 这类黑盒假设, 太脆。
